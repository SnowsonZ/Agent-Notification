# 可验证交付：以本项目为标杆的全链路 harness

状态：**P0 完成，P1 待开始**（2026-09-25 与用户对齐，本文随阶段推进更新）。基线评审见 [2026-09-25 可验证交付基线](../review/2026-09-25-harness-baseline.md)。

理论来源：用户的调研报告《低人工干预下 AI Agent 持续高质量交付：理论与全链路最佳实践》（2026-09-23，Claude 文档，未入库）。本文只保留落到本仓库的部分；报告中面向大团队的做法按单人项目裁剪。

## 1. 目标

把本项目每一类改动的完成判断，从「Agent 说做完了、人去复验」改为「开工前就有可执行的判定，完工后由 Agent 之外的机器重跑判定并留下证据」，并用 v0.8.0 的真实事故证明这套机制有效。

标杆的含义：**有效**（有数据证明）+ **可复制**（模板、脚本和文档可被其他项目照搬）。

## 2. 「可验证」的操作定义

一个任务算「已转成可验证问题」，要同时满足五条：

1. **验收有编号**：每条是命令或测试，并标注证据类型（单测 / 夹具 / 真实数据回放 / CI 断言 / 真机 UI）。AGENTS.md「验证边界」已要求区分，这里把它变成机器检查。
2. **判定在 Agent 之外**：以当前 head 的主 workflow run 为准，不采信自述。
3. **判定器本身被检验**：修复类改动的测试必须在修复前失败；关键模块测变异得分。
4. **执行者改不了判定器**：已有测试、CI、hooks、验收映射的修改或删除自动升级给评审方；新增测试不受限。
5. **证据由脚本生成**：diff 文件列表、关键行、CI 链接由脚本产出，不手写。

第 1 条做不到的（真机导航、系统授权、视觉体验）明确标为人工验收，列入清单，不假装自动化。

## 3. 角色（2026-09-25 用户决定）

| 角色 | 由谁担任 | 职责 | 不做什么 |
|---|---|---|---|
| 设计与评审 | Codex、Claude Code | 写规格与验收编号、计划与风险等级；评审（只认证据包）；执行者卡住时做顾问 | 不替执行者提交实现代码 |
| 执行 | Zcode、OpenCode、Pi | 实现、补测试、本地构建与安装开发包、推分支、开 PR | 不改已有判定器；不打 tag；不改写已推送历史 |
| 人 | 用户 | 意图与优先级；R2 以上的合并；版本号确认与发版审批；真机 UI 验收 | 不逐条审批命令、不逐行审代码 |

生成与评审由不同工具、不同模型承担，本身就是报告 2.4 节的「异构独立评审」。

## 4. 风险等级与自治（用户选定 L4）

风险等级由 CI 按改动路径判定，不由执行者自报。

| 等级 | 本项目的典型改动 | 合并方式 |
|---|---|---|
| R0 | 文档、新增测试、lint 修复 | 门禁全绿即自动合并 |
| R1 | 行为不变的重构（判据：已有测试零修改、黄金快照零差异） | 自动合并 + 抽样审计 |
| R2 | 功能改动、规格改动、界面改动 | 评审方评审 + 用户看证据包后合并 |
| R3 | 报告迁移与重写、隐私相关（快照、`hide_titles`、诊断日志）、hooks 安装（改用户配置）、CI 与发布流程、护栏本身、git 历史 | 必须由用户批准 |

## 5. 护栏分层

执行者里 Zcode 的宿主没有工具调用 hook（`~/.zcode/hooks/` 只有编辑期 lint，见 [推送通道调研](../research/2026-09-20-push-channels-per-source.md)），所以硬边界不能放在 Agent 层。

| 层 | 机制 | 能否被绕过 | 作用 |
|---|---|---|---|
| 服务端 | GitHub ruleset：`main` 禁 force push 与删除、必须经 PR 与 `build` 检查；`v*` tag 禁移动与删除；release job 走需要用户审批的 environment | 本机 Agent 无法绕过 | 硬边界 |
| git | 仓库内 `core.hooksPath`：pre-commit（禁止路径与隐私模式）、pre-push（禁推 `main` 与 tag）、reference-transaction（禁本地改写 `main` 与 tag，待实测） | `--no-verify` 等可绕过 | 与工具无关的快速反馈、防误操作 |
| Agent | Claude Code / Codex 的 PreToolUse；OpenCode 插件、Pi 扩展（拦截能力待实测）；Zcode 无 | 各家不同 | 最早的反馈，锦上添花 |

未决：所有 Agent 与用户共用同一个 GitHub 身份时，服务端无法区分操作者（例如 R2 改动能否由执行者自行合并）。P2 决定是否给执行者单独身份（机器账号或 GitHub App）。

## 6. 全流程落点

| 环节 | 本项目要建的判定 | 阶段 |
|---|---|---|
| 需求与规格 | 全部规格的验收条目编号并标证据类型；CI 校验「可自动化编号 ↔ 测试名」映射 | P4 |
| 上下文 | 一条 `verify` 命令，本机、云端、CI 同口径；工具版本锁定 | P1 |
| 规划 | 任务模板与计划模板（终态、非目标、每步验证方式、风险等级） | P4 |
| 执行 | §5 三层护栏 | P2 |
| 验证 | 金额不变量属性测试、CLI 黄金快照、七个来源的真实格式夹具、「任何重写不降级」回放、Swift 纯逻辑单测、关键模块变异测试 | P3 |
| 集成发布 | 只走 PR；CI 链接是唯一通过凭证；按路径判定风险等级；发版审批 | P1、P2 |
| 学习改进 | 失败分类法；评审发现逐条转成回归用例或自动检查 | P0、P6 |
| 度量 | 复验轮数、声称已修次数、自述不实次数、CI 轮数、逃逸缺陷、人工介入次数 | P0 基线、P6 对比 |

## 7. 标杆验收

1. **事故回放**：v0.8.0 的每类失败（基线评审 §1）都有注入用例，在新机制下被机器拦住。例如提交真实快照被拒；filter-repo 或推 tag 被拒；重新注入 R17 未排序被测试抓住；声称已修但文件未变被证据检查拦住；去掉 R2 不降级保护后回放失败。
2. **覆盖**：六份规格的验收条目全部编号；可自动化的编号在 CI 中保证有对应测试，其余进入人工验收清单。
3. **同口径**：`verify` 一条命令，三处结果一致（云端跑 Python 部分，Swift 部分由 macOS CI 负责）。
4. **真实任务试跑**：下一个功能按新流程交付，与 v0.8.0 基线（基线评审 §2）对比。

## 8. 不做什么

- 不追求全自动：UI、真机导航与 R2 以上改动保留人审。
- 不改产品行为；只做为可测而必需的重构（如状态机抽纯函数）。
- 不上 Temporal、OpenTelemetry、合并队列、金丝雀发布。
- 不打 tag、不发版（AGENTS.md）。

## 9. 阶段

| 阶段 | 内容 | 退出标准 | 状态 |
|---|---|---|---|
| P0 基线 | 失败分类、基线指标、就绪度体检、可验证性地图；本方案入库 | 基线评审与本方案入库 | ✅ 2026-09-25 |
| P1 统一入口与证据 | `verify` 命令；修复证据脚本；PR 模板要求 CI 链接与证据；风险等级判定脚本 | 三处同口径；「声称已修」「自述代替 CI」两类注入被拦住 | 待开始 |
| P2 结构护栏 | §5 服务端与 git 两层（ruleset 由用户按提供的配置操作）；Agent 层按工具补齐 | 回放「提交快照、改写历史、推 tag、改已有测试」全部被拒 | |
| P3 判定器补强 | 属性测试、黄金快照、夹具、不降级回放、变异测试 | 注入 R2、R4、R11、R13、R17、R19 类 bug 全部被抓住；变异得分基线入库 | |
| P4 规格可执行化 | 验收编号 ↔ 测试名映射与 CI 校验；任务与计划模板；模块风险等级 | 六份规格编号完成，映射检查在 CI 为绿 | |
| P5 独立评审 | 评审清单由失败分类生成；证据包格式；SwiftUI 截图回归（可选） | 评审清单覆盖回放集 | |
| P6 度量与试跑 | 事故回放集可一键运行；一个真实任务走完全流程 | 试跑数据与基线对比入库 | |

每个阶段一个 PR，按 §4 的风险等级合并；改动 CI、hooks 或测试基础设施的阶段属于 R3。
