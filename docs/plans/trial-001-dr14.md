试跑目的：按 [可验证交付方案](verifiable-delivery.md) 完整走一遍「任务 → 实现 → 机器证据 → 独立评审 → 合并」，度量结果与 v0.8.0 基线对比（方案 §9 P6）。

## 目标终态

[工作日报规范](../specs/daily-report.md) 的 DR14「隐私：正文不提取、不持久化、不输出；唯一例外是 claude CLI 首条合格用户消息截取 ≤80 字符作标题」有自动化测试覆盖：

- `harness/acceptance-gaps.txt` 不再含 DR14；
- DR14 行的「覆盖」列引用新测试；
- 新测试证明两件事：标题取首条合格用户消息且不超过 80 字符；首条消息 80 字符之后的内容，以及其余消息正文，不出现在收件箱存储与日报输出中。

## 非目标与禁止动作

- 不改产品代码。测试若发现产品行为与规范不符：停下，按下方升级包上报，这会变成一个缺陷修复任务。
- 不修改已有测试，只新增。
- 不改写已推送历史，不推 tag。

## 前置条件（不满足就停下报告）

- `python3 harness/git_guard.py status` 显示已安装；`bin/verify` 在当前 main 上通过。

预判 R2：改动规格（`docs/specs/`）；缺口清单只删不增按 R0；新增测试按 R0。以 CI 的 `harness/risk.py` 为准。
回滚方式：revert 该 PR。

## 预算（超出即停止，把升级包交给评审方）

- 同一失败的重试：最多 2 次，每次必须带新的信息
- 时长：半天

## 交付要求

- 提交前 `bin/verify` 通过，并跑一次 `bin/verify --full`；`python3 harness/acceptance.py` 显示缺口为 0
- PR 按 `.github/pull_request_template.md` 填写，附当前 head 的 CI 链接；不手写「已通过」
- 评审方用 `python3 harness/review_pack.py --base origin/main` 与 [评审提示词](../templates/review-prompt.md) 评审
